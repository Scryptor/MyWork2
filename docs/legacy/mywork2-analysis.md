# MyWork 2: как устроена старая программа

Разбор исходников `MyWork2/` (C# WinForms, .NET Framework, ~27 тыс. строк). Документ нужен, чтобы
понимать смысл старых данных и сценариев. Повторять устройство кода в новой версии **не нужно**,
важны только правила и данные.

## 1. Общая схема

```
Program.Main → Form1 (главное окно)
  ├─ при старте: проверка активации по серийнику диска (Registration) → не переносится
  ├─ BDWorker basa — единственный класс работы с SQLite (3,4 тыс. строк, SQL склеивается строками)
  ├─ TemporaryBase — статический «склад» всего: настройки, фильтры, права, текущий пользователь,
  │   кэш справочников, ссылка на главное окно
  ├─ Config.ini (IniFile) — настройки; часть лежит в секции с именем = серийник диска
  └─ settings/*.txt (Windows-1251) — выпадающие списки
```

Все формы получают ссылку на `Form1` и ходят в базу через `mainForm.basa`, а список заказов
обновляют через `TemporaryBase.SearchFULLBegin()`.

| Откуда | Что открывает |

| **Form1** (главное) | AddPosition (новый заказ), Editor (карточка заказа), Stock (склад), ClientsEditor (клиенты), Graf (отчёты), Settings, SmsMain, ColumnsEdtitor (колонки), Authorisation (вход), Registration (активация), SURPRISE (скрытые сервисные операции) |
| **AddPosition** | Printing_AKT_PRIEMA (сразу после сохранения), SmsFromEditor |
| **Editor** | Printing_AKT_PRIEMA / Printing_AKT_VIDACHI, ActPriemaPoGarantii / ActVidachiPoGarantii, Stock (подбор запчастей), States (история статусов), DataEditor (правка дат), TrackingMail, SmsFromEditor, другой Editor (заказ из истории клиента) |
| **Stock** | StockAddPosition, StockEditor (позиция; из карточки заказа — списание в заказ) |
| **ClientsEditor** | ClientAddForm, ClientEditorTrue (карточка клиента), Editor (заказ клиента) |

## 3. Ключевые сценарии

**Приём (AddPosition → сохранить).** Клиент ищется по ФИО/телефону (`BdReadFIOPhone`), иначе создаётся
в `ClientsMap`. Пишется строка в `Catalog`. ФИО, тип устройства, бренд, модель, серийник и мастер
**переводятся в ВЕРХНИЙ РЕГИСТР** при записи. В `StatesMap` пишется «Установлен статус …», в `HistoryBD` —
«Добавление новой записи». Сразу открывается акт приёма. По настройке открывается папка
`ClientFiles\<clientId>\<orderId>`.

**Карточка (Editor).** Явная кнопка «Сохранить». При закрытии сравнивает все поля с исходными и
спрашивает про несохранённые изменения. Смена статуса пишет строку в `StatesMap`.

**Выдача.** Кнопка «Акт выдачи» требует заполненных «Выполненные работы» и «Мастер». Ставит статус
«Выдан» и дату выдачи, но только если её ещё нет (повторная печать дату не переписывает). Сохраняет всё
и печатает акт. Ручная смена статуса на «Выдан» спрашивает подтверждение и тоже ставит дату выдачи,
после этого статус блокируется.

**Гарантия.** «Акт приёма по гарантии»: статус «Принят по гарантии», в комментарий дописывается
«Устройство было принято на гарантийный ремонт <дата>», печать акта. Заказ при этом **тот же**, нового
не создаётся. «Акт выдачи по гарантии»: те же обязательные поля, статус «Выдан», в комментарий —
«…выдано после гарантийного ремонта <дата>».

**Запчасти в заказ (StockEditor из Editor).** Проверяет остаток, уменьшает `Stock.CountOf`, пишет
строку в `StockMap(clientId = id заказа, ZIPId, count, price)`, **прибавляет цена × кол-во к
«Затратам» заказа**. Есть отмена списания.

**Отчёты (Graf).** За период по дате выдачи с фильтрами (мастер, адрес СЦ, тип, бренд, источник):
количество, выручка (окончательная стоимость), затраты, скидки, «без ремонта»;
**оплата мастеру = (выручка − затраты) × процент мастера** (`Mpersent` из настроек). Экспорт в Excel.

**Вход и права.** Если в `Users` нет записей, вход не спрашивается. Иначе — окно входа, права группы из
`GroupDostup` (строки «1»/«0») включают/выключают кнопки главного окна и действия в формах.

**Резервные копии.** Ежедневная копия файла базы при запуске (флаг `EveryDayBackup`), путь — `backupPath`.
Перед миграцией на версию с `ClientId` — копия в `settings/backup`.

## 4. Подводные камни в данных (важно для импорта)

- **`Catalog.Image_key` — это не картинка**, а флаг «Нужно позвонить» («1» = да). На нём построены
  кнопка «Показать ожидающие звонка» (`BdSearchPhoneWaiting`) и иконка в списке.
- **`Catalog.wait_zakaz`** — флаг «Требует заказа (запчасти)».
- **Данные клиента дублируются**: `Catalog.surname/phone/Adress/AboutUs` и `ClientsMap`. Все экраны
  читают из `ClientsMap` через `JOIN … ON c.ClientId = cm.id`. Значит, копии в `Catalog` могут быть
  устаревшими. Источник истины — `ClientsMap`, копии из `Catalog` — только для баз без `ClientId`.
- **Статусы** (точные строки): «Диагностика», «Согласование с клиентом», «Согласовано»,
  **«Принят в работу»**, «Ждёт запчасть», «Принят по гарантии», «Готов», «Выдан».
  Встречаются и произвольные значения, их нужно сохранить.
- **Штрихкод** — 12 цифр (UPC-A): 11 цифр + контрольная. Два генератора: при приёме заказа
  (`BdWrite`) код строится **по дате** — `ddMMHHmmss` + последняя цифра года; массово для заказов
  без кода (`bdBarcodeAllGenerator`) — **случайные** `4+4+3` цифры. Значит, **возможны дубли**:
  коды по дате повторяются при приёме в одну секунду и каждые 10 лет, случайные — по случайности.
  Импорт должен их найти и сообщить. Новые коды надо делать гарантированно уникальными.
- **Даты** в форматах `dd-MM-yyyy HH:mm` (заказы), `dd-MM-yyyy HH-mm` (история статусов),
  `dd.MM.yyyy hh:mm` (в тексте комментариев, 12-часовой!), плюс то, что давал `DateTime.Parse`.
- **Деньги** — строки, пустое значение заменяется на «0» (`EmptyStringToZeroMaker`). Расчёты в `double`.
- **Верхний регистр** в ФИО и названиях: показывать как есть или аккуратно форматировать при показе,
  например «ИВАНОВ ИВАН» → «Иванов Иван». Исходник в базе не менять.
- **Начальный номер заказа** задавался через `sqlite_sequence` (BaseLineNumber). В новой версии —
  настройка «следующий номер заказа», импорт продолжает нумерацию.
- **SURPRISE** — скрытые сервисные операции: заменить NULL на пустые строки, массово переименовать
  значение (например, адрес СЦ), сгенерировать штрихкоды. В новой версии: массовое переименование
  значения справочника в заказах — обычная функция редактора справочников.
- **Трек-номера** отдельно не хранятся: их пишут прямо в комментарий заказа в виде `###НОМЕР описание`
  (TrackingMail достаёт их регуляркой `###(\w+)(.*)`). Комментарий импортируется как есть, а трек-номера
  дополнительно выделяются в отдельное поле.

## 5. Что в новой версии делаем иначе (для удобства)

| Было | Будет |
|---|---|
| Отдельные окна, кнопка «Сохранить», вопрос при закрытии | Панель поверх списка, автосохранение, отмена |
| Подтверждения «Вы уверены?» на каждое действие | Действие сразу + «Отменить» в уведомлении; подтверждение только для необратимого |
| Выдача только через «Акт выдачи» | Кнопка «Выдать» (с печатью акта или без), те же проверки обязательных полей |
| Гарантия — дописка в комментарий того же заказа | Гарантийный случай как связанное событие заказа с собственной историей и датами; старые записи импортируются как есть |
| Списание запчасти правит «Затраты» вручную-автоматически | Затраты = сумма запчастей + ручные затраты, считается, а не хранится вперемешку |
| Флаги в странных колонках | Нормальные поля `need_call`, `need_parts` |
| Права = включение кнопок | Права проверяет сервер (важно для сети и телефонов), интерфейс только скрывает |
| Отчёт считается в форме | Отчёты считает сервер, одинаково для экрана и Excel |
