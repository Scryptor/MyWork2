# План 5.8. Пользователи, роли и мастера — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** мастер заказа — пользователь программы, а не значение справочника; у программы появляются экраны
«Пользователи» и «Роли», где права любой роли, в том числе готовой, выставляются галочками (решение автора,
2026-11-20; заметки «План 5.8» в `docs/superpowers/plans/README.md`).

**Architecture:** сервер уже умеет пользователей и роли (`mw-core/src/auth/{users,roles}.rs`, API `/users`, `/roles`,
защита `would_lock_out`). Добавляем: пользователя без входа и отметку «Мастер», готовые роли «Мастер» и «Приёмщик»,
удаление неиспользуемой роли, список мастеров для всех вошедших, ссылку заказа на пользователя-мастера
(`master_user_id`) при сохранённом имени текстом, перенос мастеров из справочника и из заказов в пользователей
(миграция данных и импорт MyWork 2). Интерфейс — две новые страницы настроек и выбор мастера из списка пользователей
во всех местах, где сейчас справочник «Мастера».

**Tech Stack:** Rust (Axum 0.8, SeaORM 2, SQLite + PostgreSQL), SvelteKit 3 SPA, Svelte 5 (руны), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-11-mywork3-crossplatform-design.md` (раздел 5, пункты 9 «Пользователи и
права» и 10 «Справочники»), `docs/superpowers/specs/2026-11-15-ui-design-system-design.md`. Отступление от спеки по
решению автора: «мастера» уходят из справочников (п. 10) в пользователей (п. 9) — Task 5 правит текст спеки.

## Global Constraints

- Всё из `AGENTS.md`: `Core::begin_write()`, права проверяет `mw-core`, `all_backends()`, выпущенные миграции не
  меняются, новое право или стартовые данные — только новой миграцией данных, контракт перегенерируется, поиск без
  учёта регистра — `mw_domain::search`; интерфейс — токены, `display`/`data-width`, руны, `#lib/...`, тексты в `ru.ts`,
  `createEntityEditor`/`createPagedList`, подсказки — `HelpHint`/проп `help` (план 5.7), e2e в Chromium и WebKit.
- **Никто не теряет доступ.** Пользователь без входа не считается ни в «режиме без входа» (`is_open_mode`), ни в
  защите от блокировки (`would_lock_out`): база без пользователей со входом остаётся в режиме без входа, сколько бы
  мастеров без входа в ней ни было.
- **База автора обновится сама.** Миграция данных выполняется при запуске новой версии на его настоящей базе (8 тыс.
  заказов, пользователи из MyWork 2): ничего не удаляется, имена мастеров в заказах остаются, роли и пароли не меняются.
- Никогда не запускать ничего на `~/Library/Application Support/MyWork3*` и не открывать `/Applications/MyWork.app`.
- Каждый закрытый пункт удаляется из «Заметки → План 5.8» в README в той же задаче.
- Коммиты по-русски, последняя строка `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. Обновление настоящей базы: заказы с мастерами-текстами, справочник «Мастера», пользователи из MyWork 2 с паролями —
   после миграции у каждого непустого имени мастера в заказах есть пользователь-мастер, совпадающий без учёта
   регистра пользователь отмечен «Мастер», а не задвоен; вход и права прежних пользователей не изменились.
2. База в режиме без входа (пользователей нет) после миграции и после создания мастера без входа остаётся в режиме
   без входа; первый запуск и `create-admin` работают как раньше.
3. Снять «Пользователи и права» с роли или отключить вход последнему, у кого оно есть, — отказ с понятным текстом;
   удалить роль, в которой есть пользователи, — отказ.
4. Мастер, у которого отключили учётную запись или отметку «Мастер», остаётся виден в старых заказах, но не
   предлагается для новых; переименование мастера не меняет имя в старых заказах, а ссылка `master_user_id` остаётся.
5. Пользователь без входа не может войти ни с каким паролем (тот же ответ, что на неверный пароль, ограничитель
   попыток считает попытку).

### Task 1: Сервер — пользователи без входа, отметка «Мастер», готовые роли, удаление роли, список мастеров

**Files:** новая миграция в `crates/mw-db/src/migration/` (схема) и новая миграция данных (роли), `crates/mw-db/src/entity/user.rs`,
`crates/mw-core/src/auth/{users.rs,roles.rs,sessions.rs,mod.rs}`, `crates/mw-api/src/routes/users.rs`,
`crates/mw-api/src/routes/mod.rs`, `crates/mw-api/src/auth.rs`, контракт; тесты рядом с соседями.

**Interfaces:**
- Produces: `users.can_sign_in BOOLEAN NOT NULL DEFAULT TRUE`, `users.is_master BOOLEAN NOT NULL DEFAULT FALSE`;
  `User { …, can_sign_in: bool, is_master: bool }`; `NewUser { …, can_sign_in: bool, is_master: bool }` — `login` и
  `password` обязательны только при `can_sign_in = true`; у пользователя без входа логин в интерфейсе не виден (внутренний
  уникальный логин выбирает реализация); `UserPatch { …, can_sign_in: Option<bool>, is_master: Option<bool> }`.
- Produces: `Core::delete_role(actor, id, expected_version)` → `DELETE /api/v1/roles/{id}` (право `users_manage`;
  роль с пользователями — 409 с текстом «В роли есть пользователи: N»).
- Produces: `Core::list_masters(actor) -> Vec<MasterUser { id: i64, display_name: String, active: bool }>` →
  `GET /api/v1/masters` (любой вошедший; в режиме без входа — тоже): все пользователи с `is_master`, активные первыми,
  по имени без учёта регистра.
- Produces: роли «Мастер» (`orders_edit`, `clients_view`) и «Приёмщик» (`orders_create`, `orders_edit`, `clients_view`,
  `clients_create`, `clients_edit`) — миграцией данных, только если роли с таким именем (без учёта регистра) ещё нет;
  существующие роли не трогать.

Пункты (каждый — тест, `all_backends()`):
1. Вход пользователя без входа отклоняется тем же ответом, что неверный пароль, попытка считается ограничителем.
2. `is_open_mode` и `would_lock_out` считают только активных пользователей с `can_sign_in`; тесты: база без
   пользователей + мастер без входа → режим без входа; отключить вход последнему администратору → отказ; снять
   `users_manage` с последней такой роли → отказ (есть — проверить, что остаётся).
3. Создание пользователя без входа без логина и пароля; со входом — логин и пароль обязательны (прежние проверки).
4. Включить вход пользователю без входа — нужны логин и пароль (в той же правке или `set_password` следом —
   реализация выбирает и описывает в отчёте); выключить вход — сеансы пользователя удаляются.
5. Удаление роли: без пользователей — удаляется, запись в журнал; с пользователями — 409.
6. `GET /api/v1/masters` — порядок и состав; доступен вошедшему без `users_manage`.
7. Миграция данных ролей на базе, где «Мастер» уже есть (например, из MyWork 2), не создаёт вторую.

- [ ] Step 1: тесты → падают. Step 2: миграции, ядро, API, контракт. Step 3: полные проверки Rust (обе СУБД).
- [ ] Step 4: Commit `feat(core,api): пользователи без входа, отметка «Мастер», готовые роли, удаление роли`.

### Task 2: Сервер — мастер заказа как пользователь, перенос мастеров, импорт MyWork 2

**Files:** новая миграция схемы (`orders.master_user_id`) и миграция данных (мастера → пользователи),
`crates/mw-db/src/entity/order.rs`, `crates/mw-core/src/orders/{types.rs,create.rs,update.rs,list.rs,bulk*.rs}`,
`crates/mw-core/src/settings.rs`, `crates/mw-core/src/dictionaries*.rs`, `crates/mw-legacy/src/convert/{orders.rs,access.rs,catalogs.rs}`,
`crates/mw-core/src/import/write.rs`, контракт; тесты рядом.

**Interfaces:**
- Consumes: `is_master`, `can_sign_in`, `list_masters` (Task 1).
- Produces: `orders.master_user_id BIGINT NULL` (ссылка на `users.id`); `Order.master_user_id: Option<i64>`;
  `NewOrder`/`OrderPatch` принимают `master_user_id` (`patch::nullable`); при `Some(id)` сервер пишет в `master` имя
  этого пользователя (снимок), при `None` — пустое имя; пользователь должен быть с `is_master` и активен, иначе
  `validation` с текстом «Мастер не найден или отключён». Поле `master` текстом во входных типах больше не задаётся
  (кроме импорта) — реализация решает, убрать или игнорировать, и пишет в отчёт.
- Produces: `AppSettings.default_master_user_id: Option<i64>` вместо `default_master` текста (миграция данных
  переводит текст в номер).

Пункты:
1. **Миграция данных «мастера → пользователи»** (на настоящей базе автора): все непустые имена мастеров из заказов и
   из справочника «Мастера» (без архивных и с архивными) группируются без учёта регистра (`mw_domain::search`); для
   каждого — пользователь с тем же именем (`display_name` или логин, без учёта регистра) получает `is_master = true`,
   иначе создаётся пользователь без входа с `is_master = true` и ролью «Мастер»; заказам ставится `master_user_id`;
   текст `master` в заказах не меняется; значения справочника «Мастера» уходят в архив; `default_master` → номер.
   Записи в журнале: одна сводная («Мастера перенесены в пользователей: создано N, отмечено M»). Тесты на обеих СУБД:
   два написания одного имени → один пользователь; совпадение с пользователем MyWork 2 → не задвоен; режим без входа
   сохраняется; повторный запуск миграции ничего не меняет.
2. **Заказы:** создание, правка, массовая смена мастера — по `master_user_id`; снимок имени; список заказов отдаёт
   `master_user_id`; фильтр «Мастер» в списке — по номеру пользователя (прежний фильтр по тексту — реализация решает,
   оставить ли для старых сохранённых видов, и пишет в отчёт). Тесты: смена мастера пишет историю как раньше;
   переименование пользователя не меняет `master` у старых заказов.
3. **Справочник «Мастера»** сервер больше не отдаёт в списке видов справочников для интерфейса и не принимает новые
   значения этого вида (`validation`); хранящиеся строки остаются (архив).
4. **Импорт MyWork 2:** имена мастеров из заказов и из `masters.txt` (шаблонный файл, как сейчас, отбрасывается) →
   пользователи-мастера тем же правилом, что в пункте 1 (совпадение с пользователем MyWork 2 по имени → отметка
   «Мастер»); заказы получают `master_user_id`. Синтетическая фикстура: мастер, совпадающий с пользователем MyWork 2,
   и мастер без пользователя; тест ожидаемого результата.

- [ ] Step 1: тесты → падают. Step 2: миграции, ядро, импорт, контракт. Step 3: полные проверки Rust (обе СУБД),
  `npm run verify` (типы API поменялись — интерфейс должен собираться; правки интерфейса — минимальные, остальное в
  Task 5). Step 4: Commit `feat(core,legacy): мастер заказа — пользователь, перенос мастеров`.
