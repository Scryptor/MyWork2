# MyWork 3 — новая кроссплатформенная версия «Учёт в сервисном центре»

Дата: 2026-11-11. Статус: черновик на согласование.

Связанный документ: [разбор старой программы](../../legacy/mywork2-analysis.md) — как работала
MyWork 2, смысл полей и подводные камни данных.

## 1. Зачем

MyWork 2 — WinForms-программа (.NET Framework, ~27 тыс. строк, 2015–2022) для учёта заказов в
сервисном центре по ремонту техники. Ею до сих пор пользуются, но:

- работает только под Windows;
- код тяжело поддерживать: SQL склеивается строками (инъекции), вся логика в формах и статическом
  `TemporaryBase`, печать завязана на Internet Explorer и реестр;
- данные хранятся «как попало»: даты, деньги и флаги — строки в разных форматах.

Цель — новая программа (рабочее название **MyWork 3**) с тем же смыслом работы, которая:

1. работает на Windows, macOS и Linux;
2. **без потерь переносит данные любой старой версии** (база, настройки, справочники, файлы клиентов,
   фото склада);
3. распространяется бесплатно, с открытым кодом на GitHub, сборки — в GitHub Releases.

Код пишет Claude; вклад со стороны тоже ожидается в виде pull request'ов, сгенерированных нейросетями.
Поэтому архитектура и CI рассчитаны на то, чтобы ошибки ловились автоматически: строгая типизация,
тесты на каждом уровне, проверки на трёх ОС в каждом PR.

## 2. Цели, не-цели, анти-цели

**Цели (v1.0)**
- Паритет функций со старой программой (раздел 5), кроме явно исключённого.
- Импорт старых данных: всех версий схемы (26–32 колонки в `Catalog`), всех сопутствующих файлов.
- Старые логины и пароли продолжают работать после импорта.
- Установка и запуск на Win x64, macOS (Apple Silicon + Intel), Linux x64 без установки чего-либо ещё.
- **Интерфейс спроектирован заново** (раздел 5.0): не копия WinForms-форм, а современный, удобный
  интерфейс под ежедневную работу приёмщика и мастера. Старые формы — источник функций, не макет.
- Автопроверка/автообновление из GitHub Releases.
- Три режима работы с данными (раздел 4.1): **локальный** (SQLite), **хост в локальной сети**
  (главный компьютер держит SQLite и поднимает встроенный сервер, остальные подключаются к нему),
  **выделенный сервер** (PostgreSQL). Перенос данных SQLite → PostgreSQL встроен в программу.
- Регистронезависимый поиск по кириллице (и «ё = е») одинаково во всех режимах.
- Полноценный визуальный редактор актов и наклеек (раздел 5.1); красивые акты по умолчанию,
  **2 экземпляра на листе A4** (сервису и клиенту, с линией отреза).
- Печать в один клик на выбранный принтер, включая термопринтеры этикеток.
- **Мобильный доступ**: с телефона или планшета можно зайти на сервер (хост в сети или выделенный
  сервер) через браузер и работать. Интерфейс адаптивный, на телефоне — своя раскладка экранов
  (раздел 5.3), устанавливается на главный экран как PWA.

**Не-цели v1.0**
- Отдельное нативное мобильное приложение (Android/iOS) — после v1. Его можно собрать тем же Tauri 2
  из того же интерфейса и совместить с будущим SMS-приложением.
- **SMS** — не в v1. Позже автор сделает своё Android-приложение, которое шлёт SMS с телефона
  напрямую; оно будет ещё одним клиентом того же API. Импорт старых SMS-настроек не нужен.
- Другие языки интерфейса (но строки выносятся в ресурсы, чтобы перевод был возможен).
- Отслеживание посылок Почты России (старый способ — парсинг сайта — давно не работает; API требует
  договора). Импортируются только сами трек-номера, если они есть в данных.
- Активация/лицензии/«полная версия», страница регистрации, проверка по серийнику диска —
  программа бесплатная, всё это не переносится.

**Анти-цели (провал, даже если «работает»)**
- Импорт молча теряет или искажает хоть одну запись, дату или сумму. Всё, что не удалось разобрать,
  попадает в отчёт импорта и сохраняется в исходном виде.
- Импорт изменяет исходные файлы старой программы.
- Пользователь старой версии не может найти привычную функцию (статусы, быстрые фильтры, акты,
  штрихкоды, склад).
- Новый интерфейс медленнее или неудобнее старого в частых действиях (принять устройство, найти заказ,
  сменить статус, выдать).
- Сборка требует от пользователя ставить runtime, Java, браузер и т. п.

## 3. Стек

Принцип: **ядро на Rust, интерфейс — веб-технологии в системном окне (Tauri 2)**. Нативные формы
(wxWidgets, Qt) рассмотрены и отброшены: сложные экраны (большая таблица заказов, визуальный
редактор актов, графики) на них делать тяжелее и они ведут себя по-разному на трёх ОС; Flutter/Slint/Fyne
рисуют свой интерфейс так же, как веб, но без его экосистемы.

| Слой | Выбор | Почему |
|---|---|---|
| Ядро и сервер | **Rust** (stable), async **Tokio**, HTTP **Axum** | Строгий компилятор ловит ошибки в коде, написанном нейросетями; один сервер для всех режимов |
| Доступ к данным | **SeaORM** (на `sqlx`) с бэкендами **SQLite** и **PostgreSQL**, миграции `sea-orm-migration` | Одна модель и код запросов для двух СУБД |
| Живые обновления | WebSocket (Axum) — события «заказ изменён» | Списки на всех рабочих местах обновляются сразу |
| Поиск сервера в сети | UDP-broadcast + ручной ввод адреса | Без настройки |
| Окно программы | **Tauri 2** (WebView2 на Windows, WKWebView на macOS, WebKitGTK на Linux) | Сборки 10–20 МБ, установщики msi/dmg/AppImage/deb, встроенное автообновление, подпись, в будущем — Android |
| Интерфейс | **TypeScript + Svelte 5** (SvelteKit в режиме SPA), сборка **Vite** | Мало кода, быстрый, хорошо типизируется |
| UI-компоненты | **bits-ui** (доступные примитивы без стилей) + собственная дизайн-система на CSS-переменных; иконки **Lucide** | Свой вид, светлая и тёмная темы, без «шаблонного» Bootstrap-вида |
| Таблицы | **TanStack Table** + виртуализация (**TanStack Virtual**) | Десятки тысяч заказов без тормозов, настраиваемые колонки |
| Графики | **ECharts** | Отчёты по периодам, мастерам, брендам |
| Типы между Rust и TS | **ts-rs** (генерация TS-типов из Rust-структур) + OpenAPI (**utoipa**) | API и интерфейс не расходятся; несовпадение ловится при сборке |
| Документы | **Typst** как библиотека (crate `typst`, `typst-pdf`, `typst-render`) | Типографски качественные акты; PDF и картинка для превью из одного источника, внутри процесса |
| Штрихкоды/QR | crate `barcoders` (UPC-A, как в MyWork 2) и `qrcode` → SVG в Typst | Старые наклейки и сканеры работают |
| Прямая печать | Windows: Win32 GDI через crate `windows` (растр от `typst-render`: наклейки — в DPI принтера наклеек из настроек, акты A4 — в 300 dpi); macOS/Linux: CUPS (`lp`/`lpstat`) с PDF | Печать в один клик, термопринтеры через драйверы ОС |
| Excel | **rust_xlsxwriter** | Экспорт заказов, клиентов, отчётов |
| Старые данные | `rusqlite` (чтение старой базы), `encoding_rs` (Windows-1251), `rust-ini`, `sha1` | Импорт MyWork 2 |
| Пароли | **argon2** | |
| Логи | `tracing` + файл в папке данных | |
| Тесты | Rust: `cargo test`, `insta` (снимки), `testcontainers` (PostgreSQL); интерфейс: **Vitest** + **Playwright** (сквозные сценарии через веб-сборку) | |
| Проверки | `cargo clippy -D warnings`, `rustfmt`, `svelte-check`, ESLint, Prettier | Обязательны в CI для каждого PR |
| Сервер отдельно | тот же бинарник в headless-режиме; Docker-образ + docker-compose с PostgreSQL; служба Windows/systemd | |
| CI/релизы | GitHub Actions, `tauri-action`, матрица windows/macos/ubuntu | |

Отброшено: C#/.NET (автор не хочет «виндовый» стек), Go + Wails (Wails менее зрелый, нет Typst как
библиотеки — пришлось бы возить отдельную программу), Electron (тяжёлый), нативные формы (см. выше),
перенос Typst на другой язык (огромный объём, своя копия быстро отстанет от оригинала),
HTML/Word-шаблоны актов, прямой доступ клиентов к PostgreSQL.

## 4. Архитектура

```
crates/
  mw-domain/       сущности и правила (статусы, деньги, права, поисковая нормализация) — без I/O
  mw-db/           SeaORM-сущности, миграции, репозитории (SQLite + PostgreSQL)
  mw-core/         прикладные сервисы: заказы, клиенты, склад, отчёты, права, аудит
  mw-api/          Axum: HTTP API + WebSocket, авторизация, отдача файлов, раздача веб-интерфейса
  mw-docs/         модель шаблонов → Typst → PDF/PNG; штрихкоды; Excel
  mw-print/        печать: Windows GDI / CUPS; список принтеров
  mw-legacy/       импорт MyWork 2
  mw-server/       бинарник выделенного сервера (headless)
apps/
  desktop/         Tauri 2: окно, запуск встроенного сервера, печать, локальные настройки, обновления
  ui/              Svelte-интерфейс (один для десктопа и браузера)
tests/e2e/         Playwright-сценарии
legacy/            старый код MyWork 2 (только для справки, не собирается)
deploy/            Dockerfile, docker-compose, systemd, служба Windows
docs/
```

**Главное правило: интерфейс всегда говорит с сервером по HTTP API**, в любом режиме. Отдельной
«локальной» и «сетевой» логики нет — есть один сервер (`mw-api` + `mw-core`), который либо работает
внутри десктоп-программы, либо отдельно. Через Tauri-команды идёт только то, что относится к
конкретному компьютеру: печать, выбор файлов, открытие папки, локальные настройки, обновления.

### 4.1. Режимы работы

```
Локальный                 Хост в локальной сети                 Выделенный сервер
┌──────────┐              ┌──────────────────────┐              ┌───────────────────────┐
│ Desktop  │              │ Desktop (главный ПК) │              │ mw-server             │
│ сервер на│              │ сервер на 0.0.0.0    │              │ (headless)            │
│ 127.0.0.1│              │ + SQLite            ◄┼─ HTTP ─ ПК 2 │   + PostgreSQL        │
│ + SQLite │              │                     ◄┼─ HTTP ─ ПК 3 │ (Docker/служба)       │
└──────────┘              └──────────────────────┘              └──▲────────▲───────────┘
                                                                   │ HTTP   │
                                                                 App 1    App 2
```

- **Локальный**: встроенный сервер слушает только `127.0.0.1` на случайном порту, база — SQLite-файл.
  Снаружи компьютера ничего не видно.
- **Хост**: тот же встроенный сервер открывается в сеть на порту из настроек. Другие компьютеры выбирают «Подключиться к серверу», находят
  хост через UDP-broadcast или вводят адрес. Хост должен быть включён, пока работают остальные.
- **Выделенный сервер**: `mw-server` отдельно (Docker, служба Windows, systemd) с PostgreSQL
  (SQLite там тоже допустим). Все рабочие места — клиенты.
- **Перенос**: мастер «Перейти на сервер» копирует всю базу и вложения из локальной SQLite в
  PostgreSQL (через сервер), сверяет количество записей и переключает программу в клиентский
  режим. Обратный экспорт в SQLite-файл — для резервной копии и для возврата.
- **Безопасность в сети**: HTTPS с самоподписанным сертификатом сервера. При первом подключении
  клиент показывает отпечаток/короткий код, его подтверждают на хосте, дальше сертификат закреплён
  (pinning). Вход — логин/пароль пользователя программы → токен. Если пользователей нет, сетевой
  режим требует создать хотя бы одного.
- **Одновременная работа**: оптимистическая блокировка (`version` у записи). Если двое правят
  один заказ, второй увидит, что изменилось, и выберет. Списки обновляются у всех через WebSocket.
- **Файлы** (вложения заказов, фото склада, логотип) хранятся на сервере и отдаются через API.
- **Тесты API** прогоняются дважды: на SQLite и на PostgreSQL (testcontainers). Так как локальный
  режим — это тот же сервер, отдельной проверки «по сети» не требуется.
- **Браузер и телефоны**: любое устройство в сети может открыть адрес хоста или сервера в браузере
  и работать. Прямая печать в браузере недоступна — там PDF открывается в системном диалоге
  печати или «Поделиться». Для входа с телефона хост показывает QR-код с адресом и одноразовым кодом
  подключения. Доступ снаружи локальной сети — только через выделенный сервер (за обратным прокси с
  настоящим HTTPS-сертификатом, инструкция в `deploy/`). В локальном режиме (127.0.0.1) телефоны не
  подключаются — для этого нужен режим хоста.

### 4.2. Кириллица без учёта регистра
`LIKE`/`lower()` в SQLite понимают регистр только для латиницы. Решение одинаковое для обеих СУБД:
у сущностей, по которым ищут (клиент, заказ, склад), есть колонка `search_text`. Её заполняет
приложение при каждой записи: нижний регистр по Unicode, `ё → е`, лишние пробелы убраны, телефоны —
только цифры. Поиск идёт по ней с индексом. Сортировка по ФИО в SQLite — через зарегистрированную
collation на Rust (сравнение по Unicode-правилам для русского, crate `icu_collator`); в PostgreSQL —
ICU collation `ru-RU`.

### Где лежат данные
- По умолчанию — стандартная папка данных ОС:
  Windows `%APPDATA%\MyWork3`, macOS `~/Library/Application Support/MyWork3`, Linux `~/.local/share/MyWork3`.
- **Портативный режим**: если рядом с исполняемым файлом есть файл `portable.txt`, данные лежат в
  `./data` рядом с программой (привычно пользователям Windows-версии с флешки).
- Путь к папке данных можно сменить в настройках (например, на диск с резервным копированием).
- Содержимое: `mywork.db`, `attachments/` (файлы заказов и фото склада), `backups/`, `logs/`,
  `local.json` (настройки этого компьютера: окно, принтеры, режим работы, адрес сервера;
  всё общее — в БД).

## 5. Функции (паритет с MyWork 2)

### 5.0. Интерфейс — проектируется заново
Старые формы (WinForms, 2015 г.) — перечень функций и полей, а не образец вида. Новый интерфейс
проектируется отдельно вместе с автором на макетах (раздел дополняется по итогам). Подробная спецификация интерфейса — [2026-11-15-ui-design-system-design.md](2026-11-15-ui-design-system-design.md). Уже решено:
- главные частые действия (принять устройство, найти заказ, сменить статус, выдать, напечатать)
  делаются в 1–2 действия и с клавиатуры;
- сканер штрихкода работает из любого места программы;
- **светлая и тёмная тема** с переключателем; выбор запоминается на каждом устройстве отдельно
  (локально), по умолчанию — «как в системе»; одинаковый вид на трёх ОС;
- **палитра (решение Claude)**: тёплые нейтральные серые + бирюзово-изумрудный акцент (`#0e8a7b`
  в светлой, светлее в тёмной). Цвета статусов — отдельный набор, различимый и при дальтонизме
  (статус всегда подписан текстом, цвет — дополнительно). Все цвета — токены дизайн-системы, палитру
  можно поменять в одном месте;
- всё, что в старой программе настраивалось через .txt/.ini, настраивается в самой программе.
- **Главный экран — вариант A** (выбран автором): слева разделы и «Требуют внимания», сверху быстрые
  фильтры статусов, в центре таблица заказов. Клик по строке открывает **панель заказа поверх
  страницы справа** (slide-over), где всё редактируется на месте с автосохранением; ↑↓ листают
  заказы, Esc закрывает, «Развернуть» — полная карточка.
- **Приём устройства** (макет одобрен автором): широкая панель поверх списка (клавиша N), порядок
  полей под разговор — телефон (автопоиск клиента, предупреждение о чёрном списке) → устройство
  (подсказки бренда/модели, IMEI со сканера, комплектность и состояние метками-чипами, «+ своё»
  пополняет справочник, новое поле «пароль/ключ», скрываемое) → неисправность (текст + частые
  варианты) → фото (раздел 5.4) → мастер/статус/ориентировочная цена/предоплата/комментарий.
  Справа — сводка незаполненного, прошлые заказы клиента, проверка IMEI на повторное обращение и
  гарантию. Внизу переключатели «печатать акт» / «наклейка» (запоминаются), «Принять» = Ctrl+Enter.
  Черновик сохраняется автоматически. Остальные экраны (полная карточка, клиенты, склад, отчёты,
  настройки, редактор актов, мобильные) проектируются на этапе 3 в том же стиле.
- Современные удобства: Ctrl K (поиск + команды), сканер с любого экрана, автосохранение, отмена
  действий, горячие клавиши, живые обновления, сохранённые виды, массовые действия, умные подсказки,
  перетаскивание файлов, тёмная тема, плотность таблицы.


1. **Заказы (главное окно)**: таблица с виртуализацией, настраиваемые колонки (порядок, ширина,
   скрытие — запоминаются), быстрые фильтры по статусам, «Все», «Готовые вместе с остальными»,
   «Ожидающие звонка», «Ждёт запчасть», поиск по ФИО/телефону, расширенный поиск
   (тип, бренд, модель, серийник/IMEI, мастер, статус, адрес СЦ), фильтр по адресу СЦ,
   подсветка: просроченная диагностика, «Готов», клиент из чёрного списка (цвет настраивается).
2. **Карточка заказа**: все поля старого `Catalog`, выпадающие списки из справочников, флаги
   «Требует заказа» и «Нужно позвонить», история статусов, история изменений, запчасти со склада,
   расчёт: стоимость − затраты − скидка, доля мастера (процент из настроек), открыть папку файлов заказа,
   поиск в Google по модели.
3. **Статусы**: Диагностика, Согласование с клиентом, Согласовано, Принят в работу, Ждёт запчасть,
   Принят по гарантии, Готов, Выдан (точные строки из MyWork 2). Список статусов настраиваемый
   (название, цвет, порядок); нестандартные значения из старых баз сохраняются как отдельные статусы.
   Смена статуса пишется в историю.
4. **Клиенты**: список, карточка, заметка, чёрный список, «откуда узнали», история заказов клиента,
   объединение дублей.
5. **Склад**: позиции (категория, подкатегория, бренд, модель, цвет, количество, цена, напоминание
   о минимальном остатке, до 3 фото), списание в заказ, «Докупить».
6. **Документы**: акт приёма, акт выдачи, гарантийные акт приёма/выдачи, пустой акт приёма, наклейка
   со штрихкодом (настраиваемый размер). Реквизиты фирмы, телефон, тексты договоров, валюта —
   редактируются в настройках. «Печать» — сразу на выбранный принтер (раздел 5.2), «Сохранить PDF».
   Поиск заказа по сканеру штрихкода (ввод в поле поиска) — по полю `barcode` заказа, как в MyWork 2
   (`BdReadBarcode`), а не по id; новым заказам код генерируется тем же способом, что в старой программе.
7. **Отчёты и графики**: за период, по мастеру/адресу СЦ/типу/бренду/источнику: количество заказов,
   выручка, затраты, без ремонта, оплата мастерам; экспорт отчёта в Excel.
8. **Импорт/экспорт**: экспорт заказов/клиентов в Excel, контактов в CSV (формат для телефона),
   импорт из MyWork 2 (раздел 6).
9. **Пользователи и права**: вход по логину/паролю (если пользователей нет — без входа, как раньше),
    роли с правами галочками (те же флаги, что в `GroupDostup`; готовые роли «Мастер», «Приёмщик»,
    «Администратор», свои роли), журнал действий. Мастер — пользователь с отметкой «Мастер», можно без входа
    (решение автора, 2026-11-20): заказ хранит ссылку на пользователя и его имя текстом для истории.
10. **Справочники**: бренды, устройства, неисправности, комплектность, состояние, цвет,
    выполненные работы, адреса СЦ, источники клиентов — редактируются в программе (не в .txt).
11. **Резервные копии**: ежедневная автокопия (SQLite `VACUUM INTO`), ручная копия, восстановление,
    хранение N последних. Для PostgreSQL — `pg_dump` по расписанию на сервере.
12. **Обновления**: проверка GitHub Releases при запуске, обновление через встроенный механизм Tauri по согласию. Выделенный сервер
    обновляется новым Docker-образом; клиент и сервер проверяют совместимость версий API при подключении.

### 5.1. Редактор актов и наклеек

**Модель шаблона** (JSON, хранится в БД. Из модели генерируется разметка Typst, которую пользователь
не видит; опытный пользователь может переключить блок в режим «свой Typst-код», общая для всех рабочих мест; экспорт/импорт файлом
`.mwtemplate`):
- *Тип*: акт приёма, акт выдачи, гарантийный приём, гарантийная выдача, пустой акт приёма,
  наклейка, (позже) чек/квитанция, накладная склада.
- *Страница*: размер (A4, A5, произвольный в мм для этикеток 58×40, 40×30 и т. д.), ориентация, поля.
- *Раскладка экземпляров*: «1 на лист» или «2 на лист A4» (две половины A5 одна над другой,
  пунктир «линия отреза», подписи «Экземпляр сервиса» / «Экземпляр клиента»). **По умолчанию для
  актов — 2 на лист.** Можно включить отличия между экземплярами (например, внутренний комментарий
  только в экземпляре сервиса).
- *Содержимое*: вертикальный поток блоков, блок может делиться на колонки:
  текст (с подстановками `{заказ.номер}` полей заказа/клиента/фирмы, шрифт, размер, жирность, выравнивание),
  таблица полей «название — значение», таблица запчастей/работ, логотип/картинка, штрихкод,
  QR-код, линии подписи, разделитель, отступ.
- Поток, а не свободный холст: длинная неисправность или договор не налезают на соседние блоки,
  и один шаблон корректно выглядит при любой длине текста.

**Редактор** (окно в программе): слева список блоков (добавить, перетащить, удалить),
справа свойства выбранного блока, в центре живое превью страницы (Typst → картинка, внутри процесса) на данных
выбранного реального заказа или демо-заказа. Меню «Вставить поле» со всеми доступными
подстановками на русском. Отмена/повтор. Кнопка «Сбросить к стандартному».

**Стандартные шаблоны** делаются заново и аккуратно: шапка с логотипом и реквизитами, номер и
штрихкод заказа крупно, данные устройства таблицей, договор мелким шрифтом, подписи сторон.
Тексты договоров и реквизиты из старой программы подставляются при импорте.

**Как сделано в плане 6** (крейт `mw-docs`):
- Модель шаблона пока живёт в коде, без таблицы в БД; пользовательские шаблоны, `.mwtemplate` и «свой Typst-код» — план 7.
- Шрифт документов — Libertinus Serif (OFL-1.1, из `typst-assets` 0.15.1; файлы лежат в `crates/mw-docs/fonts`):
  Typst читает TTF/OTF, а шрифт интерфейса Inter есть в проекте только как woff2. Глифа «₽» в шрифте нет,
  поэтому в документах печатается слово по таблице замен: «₽» → «руб.», «₸» → «тг», «₴» → «грн»; в интерфейсе знак остаётся.
- Данные заказа попадают в Typst отдельным `data.json`, а не подстановкой в разметку: поля заказа не могут
  внедрить в документ свою разметку. Единственный виртуальный файл кроме него — `barcode.svg`.
- Штрихкод — UPC-A; ширина модуля подгоняется под целое число точек принтера: `ceil(0,33 мм × dpi / 25,4)` точек
  (203 dpi — 3 точки, 300 dpi — 4; на узкой наклейке — не меньше 2 точек). Штрихкод только уменьшается до доступной ширины.
  Превью и печать берут один `printer_dpi` (у наклеек — DPI принтера наклеек из настроек, у актов — 300),
  поэтому выглядят одинаково.
- Печать: Windows получает растр — PNG-страницы (наклейки — в DPI принтера наклеек, акты A4 — в 300 dpi) — и рисует его через GDI; macOS и Linux
  отправляют PDF в CUPS (`lp`). Рендер идёт только через `Core::export_document`, не более двух рендеров одновременно.

### 5.2. Печать
- У каждого рабочего места свои настройки: принтер для актов, принтер для наклеек, размер этикетки,
  смещение, плотность (DPI), число копий. Хранятся локально, не на сервере.
- Кнопка «Печать» печатает сразу на выбранный принтер; «Предпросмотр» и «Сохранить PDF» — рядом.
- Windows: страница растеризуется `typst-render` — наклейка в DPI принтера наклеек из настроек, акт A4 в 300 dpi —
  и отправляется через Win32 GDI. Настоящий DPI принтера актов (`GetDeviceCaps`) — план 11.
- macOS/Linux: PDF отправляется в CUPS (`lp -d <принтер> -o media=…`), список принтеров — `lpstat`.
- Термопринтеры (Xprinter, TSC, Godex, Zebra и т. п.) работают через свои драйверы ОС: наклейка
  рисуется в точный размер этикетки и монохромно. Прямые команды TSPL/ZPL/ESC-POS — не в v1,
  добавить можно позже отдельным «драйвером» в `mw-print`.
- Тестовая печать калибровочной этикетки в настройках.
- Печать всегда выполняется на том компьютере, где нажали кнопку: сервер присылает документ,
  десктоп-программа печатает локально.

### 5.3. Мобильный доступ
- Тот же Svelte-интерфейс, адаптивная вёрстка: на узком экране — нижняя навигация, списки
  карточками вместо таблицы, крупные зоны нажатия. Ориентир — телефон от 360 px.
- PWA: манифест и иконка, установка на главный экран. Офлайн-работа не делается (данные только с
  сервера).
- Что удобно делать с телефона (приоритет при проектировании мобильных экранов): найти заказ
  (в том числе сканированием штрихкода камерой), посмотреть и сменить статус, добавить комментарий,
  **сфотографировать устройство камерой** и прикрепить к заказу (раздел 5.4), позвонить клиенту по нажатию на
  номер, проверить склад. Приём нового заказа с телефона тоже возможен, но основной сценарий приёмки —
  компьютер.
- Права те же, что на компьютере (вход по логину/паролю). Сессия на телефоне запоминается.
- Печать с телефона — PDF в системный диалог. «Отправить на печать на компьютер приёмки» — после v1.
- Сквозные Playwright-тесты прогоняются и в мобильном размере экрана.

### 5.4. Фото при приёме и в заказе
Состояние: сделаны (план 5.2) камера компьютера, файлы, обработка на сервере, черновик с очисткой и галерея с
подписью и удалением. Осталось для плана 10: «Снять телефоном» по QR (пока кнопка объясняет, что нужен режим хоста).

Фотографии устройства прикрепляются прямо в форме **нового заказа** (и позже в карточке заказа) —
это фиксирует состояние при приёме. Три способа, все в одном блоке «Фото» формы:
1. **Камера компьютера** — живое превью веб-камеры в окне, кнопка «Снять», можно несколько кадров
   подряд; выбор камеры, если их несколько.
2. **С телефона** — на форме кнопка «Снять телефоном» показывает QR-код. Телефон сканирует его,
   открывается простая страница съёмки, привязанная к этой (ещё не сохранённой) заявке; каждый снимок
   сразу появляется в форме на компьютере (через WebSocket). Работает в режимах хоста и сервера;
   в чисто локальном режиме кнопка предлагает включить режим хоста. QR содержит одноразовый
   токен, действующий только для загрузки фото в эту заявку и ограниченный по времени.
3. **Файлы** — выбор файлов или перетаскивание в окно (сюда же — вставка из буфера обмена).
На телефоне (раздел 5.3) в форме заявки и карточке заказа сразу открывается камера телефона.

Детали:
- Фото до сохранения заявки привязаны к черновику; при отмене заявки черновик и фото удаляются,
  брошенные черновики чистятся автоматически.
- На сервере: поворот по EXIF, удаление геоданных и прочих метаданных, уменьшение до разумного
  размера (длинная сторона ~2560 px), миниатюры для списков. Оригинал не хранится.
- В заказе — галерея с полноэкранным просмотром, подписью к фото и удалением (с записью в журнал).
- В шаблонах актов есть блок «Фото устройства» (миниатюры), по умолчанию выключен.
- Технически: камера через стандартный `getUserMedia` в окне Tauri. На macOS нужно разрешение на
  камеру (`NSCameraUsageDescription`); на Linux камера в WebKitGTK зависит от GStreamer — если она
  недоступна, блок предлагает «Снять телефоном» или файлы.

### 5.5. Карта склада (места хранения)
Пользователь сам «рисует» свой склад, чтобы знать, где что лежит. Детальный дизайн — когда дойдём
до модуля склада (этап 7); здесь зафиксированы требования.

- **Редактор расстановки** («Мастер склада» в настройках): план помещения, на котором ставятся и
  двигаются шкафы/стеллажи/полки (A, B, C, D…), у каждого — сетка ячеек (1, 2, 3… или ряд×колонка).
  Код ячейки вида `B-3` или `B-2-4` (шкаф-полка-ячейка), формат кода настраивается. Несколько
  помещений/точек (по адресам СЦ).
- **Позиции склада привязываются к ячейке** (одна позиция может лежать в нескольких ячейках с
  разным количеством). В карточке позиции и в запчастях заказа видно «где лежит»; на карте склада
  ячейка подсвечивается, поиск по карте («где дисплеи Samsung?»).
- **Расстановка меняется не раз**, поэтому: шкафы можно переименовывать, двигать, менять сетку,
  объединять/делить ячейки, удалять — содержимое при этом не теряется. Удаляемая ячейка с товаром
  требует указать, куда переложить. У раскладки есть история версий; перемещения товара пишутся в журнал.
- **Наклейки на ячейки и шкафы** со штрихкодом/QR (через тот же редактор шаблонов): отсканировал
  ячейку — видишь содержимое; сканируешь ячейку, потом товар — перемещение.
- На телефоне — просмотр карты и «где лежит» (раздел 5.3), удобно прямо у стеллажа.
- *Догадка Claude, уточнить при проектировании:* так же хранить место **устройств клиентов**
  (готовые к выдаче на полке «Выдача-3», в работе у мастера на столе), а не только запчастей.

## 6. Импорт из MyWork 2 (главный риск)

### Источник
Пользователь указывает **папку старой программы**. Ожидаемое содержимое (любая часть может отсутствовать):
`baza.sqlite`, `Config.ini`, `settings/*.txt`, `settings/Akts/*`, `settings/backup/*`,
`ClientFiles/<clientId>/<orderId>/*`, фото склада (пути из `Stock.Photo*`), шаблоны `Shablon_*.htm`.

Импорт работает только с **копией**: исходная папка открывается только на чтение, база копируется во
временный файл и читается оттуда.

### Определение версии
Версия определяется по реальному набору колонок/таблиц (`PRAGMA table_info`), а не по их количеству.
Отсутствующие колонки = пусто. Отсутствующие таблицы (`ClientsMap`, `StatesMap`, `Stock` и т. д.) = нет данных.

### Маппинг (старое → новое)
- `ClientsMap` → `clients`. Если `ClientsMap` нет или у заказов пустой `ClientId` (база до 30 колонок) —
  клиенты строятся из `Catalog.surname/phone/Adress/AboutUs` с объединением по «ФИО + телефон»
  (как это делала старая программа).
- `Catalog` → `orders` (+ `deleted`, + `barcode` как есть). **`Catalog.Image_key` — это флаг
  «Нужно позвонить»** («1»), а не картинка; `wait_zakaz` — флаг «Требует заказа». Данные клиента берутся
  из `ClientsMap` (экраны MyWork 2 читали их оттуда через JOIN), копии ФИО/телефона в `Catalog` — только
  для баз без `ClientId`. Трек-номера `###НОМЕР описание` из комментария выделяются в отдельное поле
  (комментарий не меняется). Дубли штрихкодов (старые коды случайные) — в отчёт; новые коды генерируются
  гарантированно уникальными. Нумерация новых заказов продолжает максимальный id. id заказов **сохраняются** (номер заказа печатается на
  актах и наклейках, клиенты его знают).
- `StatesMap` → `order_status_history`; `HistoryBD` → `audit_log`.
- `Stock` → `stock_items` (+ фото копируются в `attachments/stock/`); `StockMap` → `order_parts`
  (`clientId` в StockMap — это id заказа).
- `GroupDostup` → `roles` (флаги «True/False»-строки → bool); `Users` → `users` с исходным хэшем.
- Справочники — из значений заказов (клиентов — для «Откуда узнали»): значения и пункты полей-списков
  хотя бы из двух заказов (у двух клиентов), без учёта регистра (у гарантии — по выведенному сроку), по
  убыванию числа заказов; затем значения `settings/*.txt` (Windows-1251), которых в заказах нет (файл не
  менялся — стандартные значения MyWork 3), — они добавляются всегда; написание — из файла, иначе самое
  частое (у гарантии — с единицей срока). Текст без букв («-», «?») — не значение и не имя мастера.
  `settings/Akts/*` → реквизиты и тексты актов.
- `Config.ini` (ANSI/1251) → настройки. **Особенность**: часть настроек хранилась в секции, названной
  серийным номером жёсткого диска (`TemporaryBase.UserKey`). Импорт берёт все секции и распознаёт
  известные ключи (`backupPath`, `BlistColor`, `AdressSCDefault`, `MasterDefault`, …) в любой секции;
  если секций несколько — берёт ту, что совпадает с нынешним диском, иначе первую и пишет в отчёт.
  Ширины/порядок колонок → настройки главной таблицы. Секция `ACTIVATION` игнорируется.
- `ClientFiles/` → `attachments/orders/<orderId>/`.

### Нормализация значений
- **Даты**: в базе встречаются `dd-MM-yyyy HH:mm`, `dd-MM-yyyy HH-mm`, `dd.MM.yyyy HH:mm`,
  `dd.MM.yyyy hh:mm`, только дата, и любые форматы, которые давал `DateTime.Parse` под русской
  локалью. Парсер пробует явный список форматов (ru-RU), затем общий ru-RU-парсинг. Хранение —
  ISO-8601 локальное время. Неразобранное → `NULL` + исходная строка в `legacy_raw` + строка в отчёте.
- **Деньги**: строки с пробелами, запятыми/точками, «р.» → `INTEGER` в копейках. Неразобранное — как с датами.
- **Флаги**: «True/False», «1/0», «да/нет», пусто → bool.
- **Телефоны**: хранятся как есть (цифры), форматирование только при показе.
- **Текст**: верхний регистр, который старая программа навязывала некоторым полям, не меняется.
- **Поля-списки** (комплектность, состояние, неисправности, выполненные работы) MyWork 2 писала по-разному:
  неисправности — «пункт/ », работы — пункт и перевод строки, состояние — «пункт, », комплектность — пункты
  подряд без разделителя (делятся по строкам `komplektonst.txt` и его стартовому содержимому). Импорт делит
  их (запятая, перевод строки, у неисправностей — «/»), обрезает конечные «/», «,», «;» (точка остаётся;
  для справочника пункт сводится и без неё) и пишет в виде MyWork 3 «пункт, пункт»; исходный текст — в
  `legacy_raw`.

Каждая новая запись хранит ссылку на исходную (`legacy_id`, `legacy_raw` JSON с полным исходным рядом),
чтобы любую проблему можно было разобрать позже без исходной базы.

### Пароли
Старый хэш: `sha1_hex(UTF-16LE(password))`, без соли. При импорте хэш сохраняется с пометкой
`legacy_sha1`. При первом успешном входе пароль перехэшируется в Argon2 и пометка снимается.

### Отчёт и повторный запуск
После импорта — экран отчёта: сколько перенесено каждой сущности, список предупреждений (неразобранные
даты/суммы, заказы без клиента, отсутствующие файлы), кнопка «Сохранить отчёт». Импорт выполняется в одной
транзакции: ошибка → ничего не записано. Импорт разрешён только в пустую базу (иначе — предложить
создать новую базу для импорта).

**Повторный импорт** (на случай, если какое-то время работают в обеих программах): разрешён как
**полная замена** — текущая база MyWork 3 сначала сохраняется в резервную копию, затем создаётся заново и
импорт выполняется с нуля. Дозапись/слияние не делается (решение Claude: проще и без риска дублей).

### Тесты импорта
- В `tests/.../fixtures/` — синтетические базы каждой версии схемы (26, 27/28, 29, 30, 31, 32 колонки),
  созданные скриптом по коду старого `BDWorker.CreateBd`, с «грязными» значениями: все форматы дат,
  суммы с запятыми, пустые ClientId, дубли клиентов, CP1251-файлы, ini с секцией серийника.
- Синтетические базы генерируются скриптом в репозитории, а не хранятся бинарно.
- Тест «круговой проверки»: для каждой исходной строки есть ровно одна новая запись, все поля
  совпадают после нормализации, предупреждения — ровно ожидаемые.
- Автор предоставит реальную старую базу с папкой программы. Она используется для проверки
  локально и **не попадает в git** (только выводы: новые форматы дат/сумм → новые синтетические фикстуры).

## 7. Новая схема БД (эскиз)

`clients`, `orders` (с колонкой `version` для одновременной работы), `order_status_history`, `order_parts`, `stock_items`, `stock_photos`,
`attachments`, `users`, `roles`, `audit_log`, `dictionaries (kind, value, sort)`, `settings (key, value)`,
`service_points` (адреса СЦ). Внешние ключи включены, деньги — INTEGER копейки, даты — TEXT ISO-8601,
bool — INTEGER/boolean, первичные ключи — целые (номер заказа = id), `search_text` с индексом (раздел 4.2), `document_templates` (раздел 5.1).
Окончательная схема — на этапе реализации.

## 8. Сборка и релизы

- Тег `vX.Y.Z` → GitHub Actions (`tauri-action`) собирает:
  - Windows x64: установщик `.msi`/NSIS `.exe`;
  - macOS: универсальный `.dmg` (Apple Silicon + Intel);
  - Linux x64: AppImage и `.deb`;
  - Docker-образ сервера (GitHub Container Registry) и бинарники `mw-server` для 3 ОС.
- Манифест обновлений (`latest.json`) публикуется в релизе; программа проверяет его при запуске.
- Каждый PR: сборка и тесты на трёх ОС, clippy/rustfmt/svelte-check/ESLint, Playwright-сценарии.
  PR не сливается, пока всё не зелёное — это главная защита при вкладе через нейросети.
- В репозитории `CLAUDE.md`/`AGENTS.md` с правилами проекта и `CONTRIBUTING.md`, чтобы ассистенты
  контрибьюторов следовали тем же соглашениям.
- macOS без подписи Apple покажет предупреждение Gatekeeper; в README — инструкция. Подпись/нотаризация
  и подпись Windows — позже, при наличии сертификатов. Ключ подписи обновлений Tauri обязателен с
  первого релиза (хранится в секретах GitHub).
- Лицензия репозитория: MIT.

## 9. Порядок работ (этапы)

1. Каркас репозитория, CI на 3 ОС, `mw-domain`, `mw-db` (SQLite + PostgreSQL), `mw-core`, `mw-api`,
   тесты API на обеих СУБД.
2. **`mw-legacy` + фикстуры + тесты**, проверка на реальной базе автора.
3. Макеты нового интерфейса (компьютер и телефон) вместе с автором → дизайн-система в `apps/ui`.
4. Главный экран, карточка заказа, приём/выдача (с фото: камера компьютера и файлы), клиенты,
   справочники; десктоп-оболочка в локальном режиме.
5. Документы: модель шаблонов → Typst, стандартные акты 2-на-листе, наклейки, печать на 3 ОС.
6. Редактор шаблонов.
7. Склад с картой мест хранения (раздел 5.5, отдельное проектирование с автором), отчёты, экспорт,
   пользователи/права, бэкапы.
8. Сеть: режим хоста, поиск в сети, сертификаты, WebSocket-обновления, выделенный сервер, перенос
   SQLite → PostgreSQL, Docker/служба.
9. Мобильный доступ: мобильные раскладки экранов, PWA, вход по QR, камера (фото и штрихкод),
   «Снять телефоном» для формы приёма на компьютере.
10. Упаковка, автообновление, первый релиз.

Этапы 1–7 дают полноценную локальную версию (можно выпустить как 1.0-beta), 8–9 — сетевую и мобильную.
Адаптивность закладывается в дизайн-систему с этапа 3, чтобы этап 9 не означал переделку экранов. Так как
интерфейс с самого начала работает через HTTP API, сеть не требует переделки интерфейса.

## 10. Решения, принятые Claude (можно оспорить)

- Rust + Tauri 2 + Svelte 5/TypeScript; Axum; SeaORM (SQLite + PostgreSQL); Typst как библиотека.
- Интерфейс всегда работает через HTTP API, даже локально (встроенный сервер на 127.0.0.1).
- Клиенты никогда не ходят в PostgreSQL напрямую — только через сервер программы.
- Шаблоны — собственная модель «поток блоков» поверх Typst, а не HTML/Word и не свободный холст.
- Печать — через драйверы ОС на том компьютере, где нажали кнопку; сырые протоколы термопринтеров — после v1.
- Настройки принтеров — локальные для рабочего места, шаблоны — общие.
- Фото при приёме: веб-камера, телефон по QR, файлы; метаданные удаляются, оригиналы не хранятся.
- Мобильный доступ в v1 — через браузер/PWA; нативное мобильное приложение — после v1.
- Отслеживание Почты России, SMS, лицензирование/активация — не в v1.
- Справочники переезжают из .txt в БД.
- Id заказов и штрихкоды при импорте сохраняются; новые наклейки — UPC-A, как раньше.
- Повторный импорт — только полной заменой базы (с автокопией).
- Лицензия MIT; подпись приложений — позже.
- Название программы автор выберет позже; пока в макетах — MyWork2, в коде — нейтральное `mw`.
  Название и папка данных задаются в одном месте конфигурации, чтобы переименование было тривиальным.
